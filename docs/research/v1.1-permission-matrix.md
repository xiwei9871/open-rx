## Verified EasyRx permission surface

- Practice: 1 admin login + unlimited user accounts; admin-only user management (SRC-D5).
- User flags: `Edit Prescriptions` (create+edit Rx), `Edit EasyComments`, `Edit Templates`,
  `Finances` (view lab-generated invoices), `In House Lab` (view-only, in-house scope only).
- Only practice admin can request lab connections (SRC-D4); lab admin approves/denies (SRC-D4).
- Lab-created practice accounts auto-connect after activation (SRC-D1).
- Clinical Staff = non-login roster for impression/submitted attribution (SRC01).
- Template sharing: Copy/Edit/View grants by owner only (SRC33).
- Lab notification actions: Notify Only / Require Approval (signature) / Email Only (SRC23).
- No documented doctor-scoped Rx visibility, no submit-vs-edit flag split, no lab-side flag
  breakdown beyond "user accounts" parity.

## V-03 conclusions

1. Practice staff CAN create/submit Rx when granted edit — CONFIRMED; resolves the earlier
   open question with `rx:write` membership flag.
2. Doctor-scope (own-Rx-only) has NO evidence — EasyRS keeps org-wide visibility by default;
   optional `rx_scope=own` may be added later PROVISIONAL.
3. Lab role granularity is binary in practice (admin vs users) — EasyRS `lab_technician` gets
   operational grants (check-in, edit received Rx, ship, notify) matching documented "your lab
   techs" workflows; destructive/config actions stay admin-only (E).
4. Signature authority on approval notifications belongs to doctor/authorized signers —
   EasyRS adds `rx:approve` grant (doctor+admin default) matching "doctor or authorized
   signature" SRC23/SRC-D7.
5. All ⚠️/🔶 cells are test-gated in S1b: permission tests assert both allow and deny paths.
